# goTag — Research Recap & V1 Direction

## Sites / data sources evaluated

| Source | What it is | Verdict |
|---|---|---|
| Space-Track CDMs (Conjunction Data Messages) | Operator-grade close-approach notifications | Gated behind an SSA Sharing Agreement — not public. Even with access: prediction-only (miss distance, covariance, catalog IDs), no disambiguation signal. |
| CelesTrak / SOCRATES Plus | Free, no-login conjunction predictions, refreshed 3x/day | Open and current, but pure prediction — tells you a close approach is coming and which catalog IDs, not how to tell the hardware apart. Useful later as a trigger list. |
| ESA DISCOS | Satellite catalog | Blocked behind OAuth registration; no evidence of conjunction/event data found. Unresolved, not ruled out. |
| MMT / SeeSat-L (amateur observers) | Citizen optical tracking | Unreachable in this pass (bad URL / no web search tool). Unresolved. |
| `db.satnogs.org` | Crowdsourced satellite/transmitter **metadata** catalog | Metadata only — frequency, mode, baud rate, launch data, frame *counts*. No signal data. (User confirmed this directly.) |
| `network.satnogs.org` | Real amateur ground-station **observation network** | Open API, no auth, returns real downloadable artifacts for `status=good` observations: demodulated audio (`.ogg`), waterfall PNG, decoded frames. Bulk-scriptable. **But** scheduling is single-target — one station tracks one NORAD ID per pass, so it cannot natively capture two overlapping satellites. Gives real single-object reference signatures, not a disambiguation dataset. |

**Overall finding**: no source — gated or open — packages a ready-made "two satellites were close, here's the data that disambiguated them" dataset. The real-data path only exists at the *prediction* layer (knowing a close approach will happen), never at the *identification* layer (telling the two objects apart once close). This is a genuine gap, not a search failure.

## Packages / frameworks evaluated

| Tool | Role | Verdict |
|---|---|---|
| `sgp4` (Vallado reference impl.) | Core orbit propagator | Standard, free, matches the TLE format exactly — use this. |
| `skyfield` | Wraps `sgp4`, adds ground-site-relative geometry (az/el/range, range-rate) | **Primary library.** Needed to turn raw TEME output into anything sensor-relevant (Doppler, angular separation). |
| `poliastro` | Keplerian/perturbation experiments, delta-v maneuvers | Useful for the one-time step of deriving a companion object's state vector from ISS's via a small ΔV. Not needed for routine propagation. |
| NASA GMAT / AGI STK | High-fidelity mission tools | Overkill for a software prototype — skip. |
| GNU Radio / GPredict | RF signal synthesis / Doppler sanity-check | GPredict useful to cross-check simulated Doppler against a known-good tool. GNU Radio only needed if building an actual synthetic IQ/waveform, not just power/Doppler curves. |
| AWS Ground Station | Antenna-as-a-service for commanding own satellites | Confirmed **not applicable** — wrong problem (uplink/downlink to your own asset, not passive observation of others). |
| Rekognition | Natural-image object detection | Confirmed **not applicable** — built for faces/objects/text, not point-source photometry. |

## Key ideas and assumptions

- **Disambiguation ≠ prediction.** Every freely open source solves "a close approach will happen between catalog IDs X and Y." None solve "given two already-close objects, which physical one is which." goTag's problem is squarely the second, harder one.
- **Orbit propagation alone cannot solve disambiguation.** SGP4/TLE accuracy is ~1 km at epoch and degrades further with time — if the two objects are closer than that error, propagation can't distinguish them. This is *why* the observation-based approach (sensor data, not trajectory correlation) was chosen from the start, and the data-source research reinforces rather than contradicts that choice.
- **A real companion orbit beats an invented one.** The companion object should be derived from ISS's real TLE via a small, physically realistic delta-v (cm/s–m/s, mimicking an actual cubesat ejection/debris separation), not an arbitrary nearby orbit — this keeps the simulated scenario physically grounded.
- **"Hard to disambiguate" has a real, bounded meaning.** Based on real deployment physics: sub-km separation, few-arcsecond angular separation, in the first minutes-to-hours after a separation event, before differential drag spreads the objects apart.
- **Not all parts of a "radio signature" are equally simulatable.** Doppler shift and received signal power are physics-derived directly from the propagated relative range/range-rate — legitimate to simulate. Transmission content (actual frequency, modulation, beacon ID) is an engineering choice, not physics — for most operational satellites (esp. Starlink) it's non-public, so fabricating it is just an arbitrary label with no real-world validation path.
- **SatNOGS raises simulation quality, it doesn't replace simulation.** Real captured audio/waterfall data from `network.satnogs.org` can anchor a simulated signature in actual observed characteristics (real frequencies, modulation, noise floor) rather than inventing one from nothing — but it still can't supply the overlap/disambiguation scenario itself.
- **Optical/angular-separation is flagged as an easier first observable than RF.** It falls directly out of the same two-orbit geometry with no RF physics layer required, and still demonstrates the core "two converging/diverging objects, which is which" problem.

## V1 — pathway forward

**Primary approach: simulation**, because no real labeled disambiguation dataset exists at any access tier checked so far.

1. **Orbit layer** — pull ISS's real current TLE (CelesTrak, open), propagate with `skyfield`/`sgp4`. Derive the companion object's state vector via a small, realistic delta-v (`poliastro` for the maneuver step), not an invented TLE.
2. **Scenario window** — restrict to the physically realistic "hard to disambiguate" window: sub-km separation, minutes-to-hours post-separation.
3. **First observable: angular separation / optical.** Build and validate the simplest version of the disambiguation problem (two propagated tracks, ground-site geometry, converging/diverging angular positions) before adding RF — lower-effort, no RF physics dependency, same core problem shape.
4. **Second observable: RF, physics-only first.** Add Doppler shift and received-power curves derived directly from the propagated orbits. Explicitly do **not** fabricate transmission-content features (frequency/modulation/beacon ID) as if they were real signal — if content-level features are needed later, ground them in real SatNOGS-observed values for a comparable real satellite rather than inventing them.
5. **Real-data anchor, not replacement**: pull a handful of real `network.satnogs.org` observations (via its open API) for a comparable satellite to sanity-check that simulated noise floor, power levels, and Doppler shape are in a realistic range.
6. **Open items to resolve before/alongside V1**: confirm whether MMT/SeeSat-L or ESA DISCOS have anything usable (both unresolved, not ruled out) — low priority, revisit only if the simulated approach needs real-world validation data later.

**Explicitly deferred, not decided against**: any AWS infrastructure/architecture (Kinesis/Timestream/SageMaker/etc.) — that was raised prematurely in an earlier pass of this project and should wait until the simulation + first disambiguation algorithm actually exist and need a home.
